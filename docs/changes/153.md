- **basal-omni mini answers on the Mac's GPU as on the CPU** (`--mode eager` and `--mode mps` on Apple Silicon, torch
  before 2.14.1). PyTorch MPS in torch 2.13.0 reads no row of an embedding table that starts at element 2**31 or
  beyond: it returns zeros for it, with no error. Gemma 4 E4B's per-layer embedding table (262,144 x 10,752) has such
  rows from token id 199,729 on, and they include ":", "," and the digits, so almost every prompt read some of them
  as zeros: on the bundled questions basal-omni-2.0-mini-preview in `--mode eager` or `--mode mps` on MPS was off by up
  to 0.16 in probability from the CPU (bf16 and fp32 alike), and 1 of 48 top answers differed.
  - **Now:** on MPS with torch before 2.14.1 that table stays in host memory, as with `--ple-offload on`, and only the
    rows of each forward's tokens go to the GPU: the answers are the CPU's (fp32: within 1.4e-5; 48 of 48 top
    answers), at no cost in speed we could measure (bf16, 24 bundled questions: 1.4 s either way, single timings,
    M5 Max). Gemma 4 E2B (262,144 x 8,960, from id 239,675 on) gets the same. Any other embedding table with such
    rows is refused at start-up (none of the basal models has one), as is `basal-finetune --device mps` of E2B / E4B,
    which writes its merged checkpoint from the model.
  - torch 2.14.1 and 2.15.0 read every row, and there, on the CPU, on CUDA and for every other model, nothing changes.
    `--mode mlx` reads them whole (MLX 0.32.4). Contributed by Greg Brzezinka (@agentGreg),
    [#153](https://github.com/rkinas/basal/pull/153).
