- **Two-way models on Apple Silicon** (`--mode mlx`, `mlx-q8`, Gemma 4): a model whose basal.json has `"two_way"` is
  now read two-way by the MLX engine as by `eager` and `fast`, with mlx-lm's forward and with `--mlx-forward basal`.
  Each prompt within the limits is read whole, in a row of its own; a prompt over the limits is read one way as
  before; `--mlx-packed`, `--state-cache-gb` and `--prefix-cache` are refused for such a model. A model without
  `"two_way"` answers as before, byte for byte.
  - Measured on basal-omni-2.0-mini-preview (1,348 readouts against eager fp32 read two-way, Apple M5 Max): the 8-bit
    `-MLX` port read one way agrees on 73.4% of the top answers; with `"two_way"` in its basal.json, on 98.3%
    (`mlx-q8` from the bf16 weights: 98.6%; eager bf16: 99.4%), and no answer with a reference margin of 0.2 or more
    changes. MLX in fp32 changes none, so the rest is bf16 / 8-bit rounding.
  - A question read two-way takes 3-4x the time of the one-way read on MLX, and five questions over one state about
    10x. The published `-MLX` port has no `"two_way"` in its basal.json and is still read one way; a calibration
    fitted on one-way reads does not fit two-way reads. Contributed by Greg Brzezinka (@agentGreg),
    [#154](https://github.com/rkinas/basal/pull/154).
